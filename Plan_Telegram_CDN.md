### План реализации: Модуль «Telegram CDN Worker»

#### 1. Слой интеграции с Telegram (`src/services/telegram_service.py`)
**Цель:** Создать надежный транспорт для передачи байтов изображений в Telegram.

*   **Инициализация:** Использование `aiogram` (или `httpx` для легковесности) с токеном из `.env`.
*   **Метод `upload_photo(image_bytes, caption)`:**
    *   Принимает байты из памяти (`io.BytesIO`).
    *   Использует метод `send_photo`.
    *   **Логика извлечения:** Возвращает `file_id` самой крупной версии фото (`photo[-1].file_id`).
*   **Flood Control (Rate Limiting):**
    *   Реализация `try-except` для `TelegramRetryAfter` (ошибка 429).
    *   Если Telegram просит подождать $N$ секунд — сервис должен засыпать на $N+1$ сек и повторять попытку (до 3 ретраев).
*   **Зачем:** Это наш «мост» в бесплатное хранилище. Мы должны гарантировать, что ни один байт не потеряется из-за лимитов API.

#### 2. Слой атомарных задач (DB Concurrency)
**Цель:** Сделать воркер масштабируемым и устойчивым к сбоям.

*   **Метод `get_next_pending_album`:**
    *   Использование SQL-запроса: `UPDATE albums SET status = 'processing' WHERE id = (SELECT id FROM albums WHERE status = 'pending' LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`.
    *   **Зачем:** Это гарантирует, что если мы запустим 5 воркеров одновременно, они не будут качать один и тот же альбом. Принцип «одна задача — в одни руки».
*   **Идемпотентность:** Перед загрузкой каждой картинки воркер проверяет таблицу `images`. Если картинка с таким `yupoo_origin_url` уже есть — загрузка в ТГ пропускается, берется существующий `file_id`.

#### 3. Бизнес-логика обработки (`src/modules/worker/album_worker.py`)
**Цель:** Сценарий «полного цикла» обработки одного альбома.

*   **Этап А: Парсинг альбома.**
    *   Заход через `PlaywrightService`.
    *   Сбор всех `data-origin-src`. Если список пуст — помечаем альбом как `error` (пустой).
*   **Этап Б: Скачивание (Memory-only).**
    *   Для каждого URL картинки вызываем `playwright_service.get_image_bytes`.
    *   **Важно:** Обязательно передаем `Referer: {album_url}`, иначе Yupoo отдаст заглушку вместо фото.
*   **Этап В: Загрузка и привязка.**
    *   Отправка в `TelegramService`.
    *   Создание записи в `images` с `position` (индекс в списке).
    *   Для первой картинки (`index == 0`) устанавливаем `is_cover = True`.
*   **Этап Г: Финализация.**
    *   Перевод альбома в статус `completed` только после успешной загрузки **всех** фото.

#### 4. Контроль и отказоустойчивость (Resilience)
**Цель:** Минимум ручного вмешательства.

*   **Обработка исключений:** Если на любом этапе (кроме лимитов ТГ) происходит критическая ошибка — альбом помечается как `error`, а в поле `original_title` (или новое поле `error_log`) записывается причина.
*   **Cleanup:** После каждого альбома очистка `BytesIO` и явный вызов `gc.collect()` (опционально), чтобы при массовой загрузке не «текла» память.

#### 5. Скрипт запуска и MVP-тестирование (`scripts/run_worker.py`)
**Цель:** Удобный запуск и ограничение выборки.

*   **Параметр `--limit`:** Возможность запустить воркер на $N$ альбомов (для теста ставим 5-10).
*   **Параметр `--interval`:** Настраиваемая пауза между альбомами (рекомендуется 2-5 сек).

### Подводные камни (Senior Notes для Trae)

1.  **Lazy Loading на Yupoo:** Иногда на странице альбома картинки подгружаются только при скролле. Trae должен добавить в Playwright логику «проскроллить до конца страницы» перед сбором ссылок.
2.  **Broken Images:** Если Yupoo отдает картинку размером в 0 байт или 404 — воркер не должен падать, он должен залогировать это и пропустить файл.
3.  **Telegram Captions:** Рекомендую в `caption` к первому фото в альбоме добавлять `clean_title` и `yupoo_url`. Это упростит ручной аудит канала.
4.  **Database Session:** Убедись, что сессия БД не закрывается посреди обработки длинного альбома (на 100+ фото). Используй одну сессию на весь цикл обработки альбома.
